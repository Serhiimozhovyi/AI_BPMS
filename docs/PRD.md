# AI_BPMS — специфікація продукту (PRD)

Версія: 0.3 · Дата: 2026-10-26 · Рішення: [ADR-001](adr/ADR-001-stack.md), [ADR-002](adr/ADR-002-mcp-native.md), [ADR-003](adr/ADR-003-canvas.md), [ADR-004](adr/ADR-004-stages.md)

## 1. Що це

**MCP-native BPMS-конструктор.** Self-hosted платформа, де процес збирається на канвасі з вузлів,
а інтеграції з будь-якими системами приходять через Model Context Protocol, а не через вбудовані
конектори. Сама платформа теж є MCP-сервером, тому Claude, ChatGPT чи корпоративний агент можуть
створювати, запускати і лагодити процеси.

Одним реченням для клієнта: *«Підключіть будь-яку систему за годину, збирайте процеси на канвасі
або словами через ШІ, тримайте все на своєму сервері».*

AI_BPMS — **окремий продукт**, а не модуль одного клієнта. «Кіт 2» (CRM AgriChain) — перший пілотний
майданчик; усе специфічне для нього живе в конекторі `connectors/kit-crm` і сценаріях, не в ядрі.
Кожне впровадження розширює застосування AI_BPMS, не перетворюючись на окрему версію продукту під замовника.

## 2. Навіщо свій продукт

- **Інтеграції без власних конекторів.** Будь-який MCP-сервер (Telegram, Jira, GitHub, Microsoft 365, 1С через OData, CRM, внутрішні API) стає набором вузлів автоматично.
- **ШІ — повноцінний користувач.** Платформа — MCP-сервер; агент бачить доступні конектори, збирає сценарій, тестує, виправляє.
- **Повний контроль** над кодом, даними і ліцензією: вбудовуємо у власні продукти, продаємо, ставимо на сервер клієнта.
- **Команда .NET + Angular** підтримує продукт без перенавчання.
- Інтерфейс українською.

## 3. Користувачі

| Роль | Що робить |
|---|---|
| Автор сценаріїв (аналітик, просунутий менеджер) | Збирає процеси на канвасі або просить ШІ, тестує, вмикає |
| ШІ-агент (Claude, GPT, власний) | Через MCP: читає конектори, створює/змінює сценарії, запускає, діагностує |
| Інтегратор (розробник) | Пише MCP-сервери над внутрішніми системами за Connector Kit |
| Адміністратор | Конектори, credentials, користувачі, ролі, моніторинг |
| Глядач | Журнал виконань без права змін |

## 4. Сценарії MVP

Критерій успіху — всі три працюють у реальній компанії, зібрані **без написання коду в AI_BPMS**.

1. **Заявка з Telegram у 1С.** Повідомлення в Telegram-бот → LLM-вузол витягує структуру (клієнт, товар, кількість) → `mcp.tool` 1С: створити замовлення → відповідь у Telegram з номером.
2. **Щоденний звіт.** Cron 07:00 → `mcp.tool` 1С/CRM: вибірка за день → Code-вузол: агрегація → лист через Microsoft Graph з таблицею.
3. **Агент будує процес.** Користувач у Claude Desktop каже: «Коли приходить лист з темою "Рахунок", збережи вкладення і повідом у Telegram-чат бухгалтерії». Claude через MCP AI_BPMS викликає `describe_connectors` → `create_workflow` → `validate_workflow` → `run_workflow` на тестових даних, і сценарій з'являється на канвасі.

## 5. Функції MVP

**Конектори (MCP-клієнт)**
- реєстрація MCP-сервера: stdio (команда + аргументи) або Streamable HTTP (URL + auth)
- discovery tools, кеш схем, оновлення, статус з'єднання, тест виклику
- credentials прив'язуються до сервера; у сценарії — лише id

**Канвас**
- палітра: `core.*` + tools усіх підключених серверів (пошук, групи за сервером)
- з'єднання, видалення, копіювання, undo/redo, автозбереження, версії
- панель вузла: форма з JSON-схеми tool, поле виразу з підказками, Monaco для Code
- тестовий запуск усього сценарію або одного вузла; input/output кожного вузла; pinned data
- живий статус під час тестового запуску (SSE)

**Виконання**
- тригери: ручний, webhook, розклад; polling-тригер над будь-яким `mcp.tool`
- логіка: IF, Switch, Merge, Loop, Wait, Set, Code (JS у Jint)
- `mcp.tool` з таймаутом, retry, `continueOnFail`
- `ai.llm`: виклик моделі (Claude/OpenAI/локальна через OpenAI-сумісний API) зі structured output за JSON-схемою
- стан кожного кроку в БД; відновлення після падіння воркера; error-workflow

**AI_BPMS як MCP-сервер** — tools і resources з [ADR-002](adr/ADR-002-mcp-native.md), авторизація API-ключем.

**Журнал виконань** — список, фільтри, деталі по вузлах, повторний запуск, скасування.

**Credentials** — шифроване сховище: API key, Basic, Bearer, OAuth2 (authorization code), довільний JSON для MCP-серверів.

**Доступ** — користувачі, ролі admin/editor/viewer, email+пароль, API-ключі для MCP і REST.

**Вбудовування** — REST API з OpenAPI; канвас як web-component `<openbp-canvas workflow-id>` для вставки в інші продукти.

## 5a. Модель процесу (v0.3, [ADR-004](adr/ADR-004-stages.md))

Одиниця виконання — **граф вузлів** (тригер → логіка → `mcp.tool`/`ai.*`), той самий для автоматизацій,
чатботів, шедулерів і бізнес-процесів. Для бізнес-процесів над графом стоїть необов'язковий шар **етапів**:

- **Етап** — група вузлів з назвою, виконавцем (доріжка/роль), строком і правилами переходу. Стан етапу
  (`pending` → `active`/`overdue` → `done` | `skipped` | `cancelled`) рушій обчислює з виконання; окремої
  моделі, яку треба синхронізувати з графом, немає. Етап завершується тим, що його кроки справді виконались.
- **Правила переходу** — умова, що перевіряється, коли виконання виходить з етапу; режим `block`
  (чекати виправлення або відхилення з причиною) чи `warn` (пройти, зафіксувати порушення). Правила діють
  однаково для ручних, автоматичних і зовнішніх переходів.
- **Відхилення** — продовження всупереч правилу з обов'язковою причиною; фіксуються правило, версія
  сценарію, користувач або система, час і дані переходу.
- **Порушення** — окремий від стану процесу список невиправлених правил; після виправлення умова
  перевіряється повторно, історія лишається в audit log.
- **Паралельні гілки** — явні режими об'єднання (`all` / `any` / `count`); завершення чи скасування процесу
  закриває всі незавершені очікування й задачі.
- **Контракт взаємодії** — один для REST, `/mcp` і web-component: стан етапів виконання, доступні дії,
  невиконані умови; дія з будь-якої системи передає результат у процес. Сутностей конкретного клієнта в
  контракті немає.
- **Узгодження даних** — стан бізнес-об'єкта живе у системі-власнику, AI_BPMS зберігає стан процесу;
  пропущені події надолужує звірка (`mcp.poll`, `mcp.waitFor`), дублікати відсікає ключ кореляції.

**Критерій готовності продукту:** новий бізнес-процес створюється налаштуванням, нова система підключається
через інтеграцію (MCP-сервер за Connector Kit + контракт взаємодії) без змін у ядрі. Перевірка — після
пілоту в Кіті до того самого контракту підключається другий застосунок.

## 5b. Обсяг автоматизацій

Матриця потрібних можливостей — шедулери, чатботи, події, обробка даних, інтеграції — і критерії їх
приймання (приклад у `examples/` з тестом) ведуться в `docs/capabilities.md`. Орієнтир — реальні сценарії
компанії (бот психологічної підтримки, звіти, БП продажів), а не паритет з n8n.

## 6. Поза MVP

MVP (фази 0–4) виконано 2026-10-24. Далі — за попитом пілотів, задачі в `BACKLOG.md`:

- фаза 5 — БП продажів поверх CRM «Кіт 2» (довге очікування, `mcp.waitFor`, кореляція, конектор `kit-crm`);
- фаза 6 — функціональність BPMS: людські задачі й погодження, форми, підсценарії, таблиці рішень,
  проєкти з правами, audit log, каталог конекторів, ШІ-агент, push-тригери;
- фаза 7 — етапи й правила (§5a), контракт взаємодії, узгодження даних, перевірка незалежності продукту.

Досі поза планом: мультитенантність і білінг, маркетплейс конекторів, мобільний UI.

## 7. Нефункціональні вимоги

- до 50 одночасних виконань на воркері; горизонтальне масштабування воркерами
- виконання переживає перезапуск воркера
- історія виконань — налаштовуваний строк (30 днів за замовчуванням)
- розгортання — Docker Compose на одному сервері; тільки Postgres як зовнішня залежність
- секрети ніколи не потрапляють у логи, журнал і відповіді API/MCP
- p95 запуску webhook-сценарію з 5 вузлів без зовнішніх викликів — < 500 мс

## 8. Ліцензія і продаж

Вихідний код AI_BPMS — **пропрієтарний** (клієнт отримує образи + право на self-hosted).
Усі залежності — MIT/Apache-2.0/BSD/PostgreSQL (див. ADR-001). Connector Kit і шаблон конектора —
MIT, щоб екосистема конекторів росла назовні. Остаточне формулювання ліцензії — з юристом до
першого продажу.

## 9. Відкриті питання

- Реальна компанія для пілоту сценаріїв 1–3 і доступ до її 1С.
- Якою моделлю за замовчуванням працює `ai.llm` у коробці (ключ клієнта / наш проксі).
- Чи потрібен Entra ID для першого клієнта (тоді переноситься у MVP).
