# ADR-004. Етап бізнес-процесу як шар над графом

Статус: **прийнято** (F7-01, 2026-10-26) · Дата: 2026-10-26

## Контекст

Власник 2026-10-25 сформулював напрям розвитку: OpenBP — окремий продукт для побудови й виконання
бізнес-процесів і автоматизацій, «Кіт 2» — перший пілот. Базова сутність для людей бізнесу — **етап БП**:
дії, виконавці, умови завершення, строки й переходи. Поверх етапу потрібні правила переходів з режимом
«блокування / попередження», відхилення з обов'язковою причиною, стан невиправлених порушень, явні
правила завершення паралельних гілок і єдиний контракт «стан етапу · доступні дії · невиконані умови»
для будь-якої підключеної системи.

Сьогодні OpenBP виконує **граф вузлів** (`docs/workflow-format.md`): тригер → `core.*` / `mcp.*` / `ai.*`,
без циклів. Бізнес-вигляд (`docs/business-view.md`, F3-65…F3-69) показує той самий граф доріжками й
кроками; рішенням власника 2026-10-24 етапи туди **не** додавали, бо тоді вони були лише розміткою, яка
нічим не керує. Рушій Кіт V1 — BPMN-модель з власними переходами, яку OpenBP згодом має замінити; саме
розходження «намальована схема ≠ те, що виконується» — проблема, якої ми уникаємо.

Є два способи дати етапу владу над виконанням: зробити етап новою одиницею виконання з власними
переходами (другий рушій, по суті BPMN) або лишити одиницею виконання граф, а етап зробити шаром над
ним, який рушій обчислює і яким керується на межах.

## Рішення

Етап — **необов'язковий шар над графом**. Одиниця виконання лишається вузол; етап групує вузли,
має стан, умову завершення, строк і правила переходу, які рушій застосовує на ребрах, що виходять
з етапу. Сценарії без етапів (боти, шедулери, інтеграції) працюють як зараз.

### 1. Формат (`stages[]`, formatVersion лишається 1)

```json
"stages": [
  {
    "id": "st_approve",
    "name": "Погодження",
    "nodes": ["n_assign", "n_wait_decision"],
    "owner": { "lane": "kit" },
    "due": { "amount": 2, "unit": "businessDays" },
    "transitions": [
      {
        "to": "st_contract",
        "rules": [
          {
            "id": "r_budget",
            "condition": "{{ $json.sum <= $vars.approvalLimit }}",
            "mode": "block",
            "message": "Сума перевищує ліміт погодження. Потрібне рішення керівника."
          },
          {
            "id": "r_note",
            "condition": "{{ $json.note != '' }}",
            "mode": "warn",
            "message": "Немає коментаря до рішення."
          }
        ]
      }
    ]
  }
]
```

- `nodes` — вузли етапу; кожен вузол належить щонайбільше одному етапу; вузли без етапу дозволені.
- Етап зв'язний у графі після згортання технічних вузлів (валідатор перевіряє); ребра між вузлами одного
  етапу — внутрішні, ребро з вузла етапу A у вузол етапу B або без етапу — **перехід**.
- `owner` — хто виконує етап: доріжка бізнес-вигляду (`lane`), роль або вираз; на бізнес-вигляді етапи
  стають колонками (компонент «Етап N» AC-Kit уже є, F3-69 використовує його кольори).
- `due` — строк від входу в етап: `amount`/`unit` (`minutes` … `businessDays`, робочі дні — пн–пт за
  `settings.timezone`) або `until` (вираз дати).
- `transitions[].rules[]` — правила переходу (§3). `transitions` без `to` діє на всі виходи з етапу.
- Усе необов'язкове; невідомі поля зберігаються. Коди валідатора: `STAGE_ID_DUPLICATE`,
  `STAGE_NODE_UNKNOWN`, `STAGE_NODE_IN_TWO_STAGES`, `STAGE_NOT_CONNECTED`, `STAGE_TRANSITION_UNKNOWN`,
  `STAGE_RULE_ID_DUPLICATE`.

### 2. Стан етапу — обчислюється рушієм, не зберігається окремо від виконання

| Стан | Коли |
|---|---|
| `pending` | жоден вузол етапу не стартував |
| `active` | є вузол етапу `running`/`waiting`, або є пройдений вузол і ще не пройдено перехід |
| `overdue` | `active` і `now > dueAt` (підстан, не окремий статус) |
| `done` | пройдено перехід з етапу або останній вузол етапу завершився без вихідних ребер |
| `skipped` | виконання завершилось, етап так і не став `active` (гілка не дійшла) |
| `cancelled` | виконання скасовано чи завершилось помилкою, поки етап був `active` |

Рушій пише таблицю `execution_stages (execution_id, stage_id, status, entered_at, due_at, exited_at)`
при збереженні кроку (той самий `SaveStepAsync`); з неї — SLA, журнал і контракт §4. Умова завершення
етапу — структурна (перехід пройдено). Окремої «умови завершення» виразом немає: якщо потрібна умова,
вона стоїть у вузлі етапу (`core.if`, `mcp.waitFor`, `core.approval`) — так етап завершується тільки тим,
що справді виконалось, а не формулою поруч.

### 3. Правила переходу, відхилення, порушення

- Правило перевіряється **на переході** — коли рушій бере ребро з етапу; `condition` — звичайний вираз над
  items на цьому ребрі (`$json`, `$node`, `$vars`). `true` — правило виконане.
- `mode: block`: правило не виконане → виконання переходить у `waiting` з причиною `STAGE_RULE_BLOCKED`,
  етап лишається `active`, створюється порушення `open`. Продовжити можна двома способами: умова стала
  істинною (повторна перевірка при `resume` або події) або **відхилення** —
  `POST /executions/{id}/overrides { ruleId, reason }` від `editor`/виконавця етапу; тоді порушення стає
  `overridden`, ребро проходить.
- `mode: warn`: правило не виконане → порушення `open`, перехід проходить. Якщо перехід ініціює людина
  (рішення в `/tasks`, дія через контракт §4), клієнт зобов'язаний показати `message` і передати `reason`;
  без причини сервер відповідає 422 `STAGE_RULE_REASON_REQUIRED`. Автоматичний перехід причини не має —
  порушення лишається `open` до виправлення.
- Порушення — таблиця `violations (execution_id, stage_id, rule_id, workflow_version_id, status
  open|resolved|overridden, actor_user_id|actor_system, reason, context jsonb, created_at, resolved_at)`.
  `context` — items переходу після scrubbing секретів (§8 architecture). Версія правила = версія сценарію
  (версії незмінні, F3-61), окремої версійності правил немає.
- `open` порушення **не зупиняє** процес (`warn`) і не є станом процесу: стан етапу і список порушень
  живуть окремо. На кожній наступній події етапу (вузол етапу завершився, перехід, `resume`) рушій
  переобчислює `open` правила етапу; виконане → `resolved`. Історія змін — audit log (F6-15) з подіями
  `violation.opened|resolved|overridden`.
- Для автоматичних кроків `block` майже не має сенсу (невиконана умова — це інша гілка `core.if`);
  режим існує для переходів, які ініціює людина чи зовнішня система.

### 4. Контракт взаємодії (той самий для REST, `/mcp`, `<openbp-canvas>`)

Application-сервіс `IStageService` (правило 4 CLAUDE.md):

- `GET /api/v1/executions/{id}/stages` → `[{ id, name, status, enteredAt, dueAt, exitedAt, owner,
  violations: [{ ruleId, status, message, createdAt }], actions: [{ id, kind: task|override|resume, title, taskId? }],
  unmet: [{ ruleId, message }] }]` — стан, доступні дії (відкриті задачі F6-02 цього етапу, дозволені
  відхилення, пробудження `core.wait` у режимі `webhook`), невиконані умови.
- `POST /api/v1/executions/{id}/stages/{stageId}/actions/{actionId} { data?, reason? }` — виконати дію:
  завершити задачу, відхилити правило, пробудити очікування; результат передається у виконання як items.
- MCP tools `get_execution_stages`, `act_on_stage`; resource `openbp://executions/{id}/stages`.
- `<openbp-canvas view="business" execution-id>` малює етапи колонками зі станом і діями з цього ж контракту.
- Кореляція з об'єктом зовнішньої системи — `settings.correlation` (F5-04): клієнт знаходить виконання
  за `correlationKey` (`GET /executions?correlationKey=`), далі працює з етапами. Сутностей Кіта
  у контракті немає; все специфічне для Кіта — у `connectors/kit-crm` і сценарії.

### 5. Паралельні гілки й завершення

- `core.merge` (typeVersion 2) отримує `mode: all | any | count` (+ `count`): `any`/`count` пропускають
  першу/N-ту гілку, решта гілок **скасовуються**: їхні `waiting` вузли й відкриті задачі закриваються.
- Завершення або скасування виконання закриває все незавершене: `core.wait` у `waiting` → `cancelled`,
  задачі `tasks` (F6-02) → `cancelled` з посиланням на причину, етапи `active` → `cancelled`, `pending` → `skipped`.
  Задача не може лишитись `open` у завершеному виконанні — інваріант, який перевіряє тест.

### 6. Узгодження даних між системами

Принцип: **стан бізнес-об'єкта живе у системі-власнику** (угода — у Кіті, замовлення — у 1С), OpenBP
зберігає лише стан процесу (виконання, етапи, порушення). Сценарій читає стан через tools, не кешує
його як істину. Пропущені події надолужує страхувальна звірка — `mcp.poll`/`changes_since` поруч із
push-тригерами (F6-13), `mcp.waitFor` перечитує умову, кореляція відсікає дублікати. Правила — у
`docs/consistency.md` (F7-07) і в шаблоні Connector Kit.

## Наслідки

- Формат змінюється додаванням необов'язкових полів — `formatVersion` 1, старі сценарії валідні. Зміна
  формату — задача `fable` (F7-01), реалізація — нічні задачі F7-02…F7-05.
- Рішення власника 2026-10-24 «без етапів» у бізнес-атрибутах переглянуто: етап повертається не як
  розмітка, а як сутність, що керує виконанням. `business.lanes`/`steps` лишаються без змін.
- Боти, шедулери й інтеграції не отримують зайвої складності: без `stages` рушій працює як раніше.
- З'являються дві таблиці (`execution_stages`, `violations`) і один сервіс (`IStageService`); ретеншн
  F4-07 чистить їх разом із виконанням.
- Критерій незалежності продукту (roadmap фаза 7): після пілоту в Кіті друга система підключається через
  той самий контракт §4 без змін у `src/`; архітектурний тест забороняє сутності й API Кіта в `src/` (F7-08).

## Відхилені альтернативи

- **Етап як окрема модель з власними переходами (BPMN-подібно).** Два рушії, дві схеми, що розходяться;
  бізнес-схема знову стає малюнком. Саме від цього тікаємо в Кіт V1.
- **Етап лише як розмітка бізнес-вигляду** (рішення 24.10). Не дає строків, правил, порушень і контракту —
  того, що потрібно власнику процесу.
- **Умова завершення етапу окремим виразом.** Дає етапу «закритись» формулою, коли реальні кроки не
  виконались; залишаємо завершення структурним, умови — у вузлах.
- **Окрема версійність правил.** Зайве: версії сценарію незмінні, порушення посилається на `workflow_version_id`.
