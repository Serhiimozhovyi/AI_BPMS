# ADR-005. Проєкт як робочий простір: таблиці, сторінки застосунку, шаблон

Статус: **прийнято** (F8-01, 2026-10-28) · Дата: 2026-10-28

## Контекст

Власник 2026-10-28 запропонував зробити з OpenBP середовище, де кожен прикладний застосунок компанії — проєкт
з власними вкладками: адмінка застосунку, адмінка бізнес-процесів (сценарії) і дані застосунку, видимі в системі.
Перший такий застосунок — бот психологічної підтримки за ТЗ «Розширення корпоративного Telegram-бота Астарти
функціоналом психологічної підтримки» (жовтень 2026): окремий Telegram-бот (у корпоративному боті буде лише
посилання), консультації, БСТ, події, матеріали, нагадування, кабінет психолога й базова аналітика.

Що є сьогодні:

- Проєкти вже існують (F6-14): група сценаріїв — це проєкт з учасниками `editor`/`viewer`; сценарії, credentials,
  конектори й API-ключі прив'язані до проєкту; перевірка прав — в application-шарі.
- Таблиці даних (F6-11) — спільні для інстансу: `data_tables` + `data_rows (key, data jsonb)`, без проєкту, без
  обмежень цілісності й без атомарних операцій над кількома рядками.
- Адмінка бота — окремий застосунок `connectors/psy-support` (F3-33…F3-35): своя база, свій вхід, свої сторінки на
  Angular, MCP-tools для сценаріїв. Сценарій бота F3-31 працює через ці tools.

Варіанти, які розглядали:

1. **Вбудувати psy-support вкладкою** (iframe + одноразовий код входу через OpenBP). Найдешевше, але кожен новий
   застосунок знову потребує власного бекенду, фронтенду й входу, а «дані видно в системі» лишається побажанням.
2. **Переписати адмінку бота в `apps/web`** як розділ OpenBP. Порушує незалежність продукту (F7-08): у коді
   з'являється предметна область одного клієнта.
3. **Побудувати бота і його адмінку з нуля на примітивах OpenBP** — таблиці проєкту, сторінки без коду, сценарії —
   і зберегти як шаблон проєкту. Найдорожче з трьох, але далі будь-який застосунок такого класу збирається без коду.

Власник вибрав варіант 3 («переписати в OpenBP», потім «з нуля за ТЗ»).

## Рішення

**Проєкт — робочий простір.** Сторінка проєкту `/projects/:id` має вкладки: Огляд · Застосунок · Сценарії ·
Таблиці · Підключення · Учасники. Загальні сторінки («Сценарії», «Таблиці», «Виконання») лишаються й фільтруються
за проєктом у шапці, як зараз.

### 1. Таблиці належать проєкту і тримають правила цілісності

- `data_tables.project_id` (`null` — спільна таблиця, як сьогодні); назва унікальна в межах проєкту; права — права
  проєкту (viewer читає, editor пише, чутливі колонки — нижче).
- Нові типи колонок: `datetime` (момент часу з поясом, у БД — ISO UTC), `enum` (`values[]`), `ref` (`table` —
  ключ рядка іншої таблиці того самого проєкту або спільної), `user` (id користувача OpenBP).
- Обмеження на таблиці (`constraints` jsonb): `required: [column]`, `unique: [{ columns, where? }]` — часткова
  унікальність з умовою в синтаксисі `where` вузла (напр. «один слот — один активний запис»:
  `{ columns: ["slot_id"], where: [{ column: "status", operator: "eq", value: "active" }] }`).
- Колонка з `sensitive: true` (телефон, `telegram_id`): її значення не бачить viewer без ролі застосунку, вона не
  потрапляє в сторінку «Показники», експорт шаблону і `openbp://tables/{id}`; читання чутливих колонок через REST/MCP
  пишеться в audit log.
- Нові операції вузла `core.dataTable` (typeVersion 2, v1 працює як раніше): `insertIf { values, where, maxCount }`
  — вставка лише коли рядків за `where` менше ніж `maxCount` (місткість події, ліміт активних консультацій);
  `increment { key, column, by }`; `count { where }`. `insert`/`upsert`/`insertIf` поважають `unique`: порушення —
  результат `{ inserted: false, reason: "unique" | "capacity" }`, а не помилка вузла, щоб сценарій міг відповісти людині.
- Реалізація — у `PostgresDataTableStore`, одна транзакція з `SELECT … FOR UPDATE` рядка `data_tables` (серіалізує
  запис у таблицю; обсяги таблиць проєктів — тисячі рядків, не мільйони) і перевіркою `unique`/`maxCount` усередині.
  Схема `data_rows` не змінюється.

### 2. Сторінки застосунку — конфігурація, а не код

- Таблиця `project_pages (id, project_id, key, name, kind, definition jsonb, roles jsonb, sort_order, updated_at)`.
  `kind`: `list` (таблиця з колонками, фільтрами, пошуком, діями над рядком), `detail` (поля рядка + пов'язані
  списки за колонками `ref`), `form` (створення/правка рядка тим самим рушієм форм, що й `core.formTrigger`, F6-03),
  `metrics` (лічильники й агрегати по таблицях без чутливих колонок).
- Дія на сторінці — або пряма операція над рядком (`update`, `delete`), або запуск сценарію проєкту з рядком і
  користувачем на вході з очікуванням результату (як `run_workflow` з `wait`); результат показується людині.
  Так «Скасувати запис» в адмінці й у боті — один сценарій.
- `definition` описує лише таблиці, колонки, вирази й сценарії проєкту; рендерить сторінки `apps/web` компонентами
  AC-Kit. Жодних назв предметної області в `src/` і `apps/web/src` — архітектурний тест F7-08 поширюється на
  сторінки.
- Редагує сторінки editor проєкту через форму-конструктор; вільний макет (drag-and-drop) — поза цією фазою.

### 3. Ролі застосунку

- Проєкт оголошує свої ролі (`workflow_groups.app_roles` jsonb: `[{ key, name }]`), учасник отримує одну
  (`project_members.app_role`, `null` — без ролі). Ролі проєкту `editor`/`viewer` і далі керують сценаріями й
  таблицями; роль застосунку керує лише сторінками.
- Сторінка перелічує ролі, яким видна, і може звузити рядки виразом з `$user` (`{{ $user.id }}`, `{{ $user.email }}`,
  `{{ $user.appRole }}`). Користувач, який має в проєкті лише роль застосунку (глобальний viewer), після входу
  потрапляє на сторінки застосунку й не бачить редактора сценаріїв.
- Перевірка — в application-шарі, одна для REST, UI і `/mcp`.

### 4. Шаблон проєкту

- Експорт/імпорт проєкту одним JSON (`docs/projects.md` §5): опис і ролі, таблиці (схема, обмеження, за бажанням
  рядки — напр. `settings`), сторінки, сценарії, маніфест конекторів і credentials з перемапінгом, як у F6-09.
- Шаблони живуть у `examples/projects/<назва>/` і встановлюються одним імпортом (UI, REST, CLI `openbp import-project`).
- Бот психологічної підтримки — перший шаблон `examples/projects/psy-support/`. Після перемикання продакшн-бота
  `connectors/psy-support` і приклад F3-31 вилучаються (F8-12).

### 5. Чого не робимо

- Не додаємо другий рушій даних: таблиці лишаються `data_rows` з jsonb; реляційні звіти, зовнішні ключі БД і
  мільйони рядків — це конектор `sql` (F6-31), а не таблиці проєкту.
- Не вбудовуємо чужі застосунки iframe-ом і не робимо SSO для них у цій фазі: якщо попит з'явиться, це окремий ADR.
- Не змінюємо формат сценарію: нові можливості — лише операції вузла `core.dataTable` v2.

## Наслідки

- Будь-який застосунок класу «дані + адмінка + бот/процеси» збирається в OpenBP без коду і переноситься шаблоном;
  предметна область живе в конфігурації проєкту, а не в `src/`.
- Таблиці стають придатними для даних з правилами (місткість, унікальність) — те, що в n8n трималося на
  «перечитати і відкотити».
- Ціна: фаза 8 — 11 PR до запуску бота на тестовому боті (`BACKLOG.md`, «Фаза 8»); найбільші — таблиці (F8-02),
  сторінки (F8-04) і шаблон бота (F8-08, F8-09).
- До перемикання продакшн-бот, n8n і таблиця Google Sheets не змінюються; psy-support працює як зараз.
