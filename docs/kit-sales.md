# БП продажів на CRM «Кіт 2»: проєкт (F5-01)

Статус: **чернетка на погодження власником**. Після погодження за цим документом уточнюються F5-02…F5-07.

Аналіз розривів, з якого виріс документ: https://claude.ai/artifact/7mFpPv61uPKxGJ7rag8nsT

## 1. Межі

- OpenBP розвивається **окремо** від «Кіт 2» (LAMS-Kit). У коді, БД і налаштуваннях Кіта нічого не змінюємо. Згодом OpenBP стане частиною Кіта й замінить його BPMN-рушій, але це окремий етап за рішенням власника.
- Кіт для OpenBP — зовнішня система за OData API (`/odata/<Set>`). Прямих підключень до SQL Server Кіта немає.
- Усе спілкування з Кітом іде через MCP-конектор `kit-crm` (F5-05). Сценарії не роблять HTTP-запитів до Кіта напряму.
- Подій назовні Кіт не віддає, тож OpenBP **опитує** зміни (`mcp.poll` + `changes_since`). Push від Кіта (Hangfire-job → webhook OpenBP) можливий пізніше, але це зміна коду Кіта, тобто рішення власника. Тоді сценарії перемкнуться з `mcp.poll` на `core.webhook` без змін решти графа.
- Перевірки на живому Кіті проводимо лише разом із власником на dev-стенді, ніколи на проді.

## 2. Довге очікування (F5-02)

Зараз `core.wait` v1 тримає слот воркера через `Task.Delay` і обмежений 1 год. Процес продажу чекає дні й тижні, тож потрібен стан очікування, що живе в БД.

### 2.1. Стан `waiting`

- Новий стан виконання `waiting` (між `running` і фінальними). Колонки `executions.resume_at` (коли будити) і `executions.waiting_node_id` (який вузол чекає).
- Вузол, що хоче чекати, повертає рушію **призупинення**: `ctx.Suspend(resumeAt, state)`, де `state` — невеликий JSON вузла (наприклад, лічильник перевірок у `core.waitFor`). Рушій записує крок зі статусом `waiting` і вхідними items, не планує нових вузлів, дочікується завершення паралельних гілок, що вже виконуються, і завершує прохід із результатом `Suspended(resumeAt)`.
- Якщо одночасно призупинились кілька гілок, `resume_at` = найраніший час. На пробудженні кожен вузол у `waiting` сам вирішує, чи настав його час: якщо ні, він знову призупиняється зі своїм `resumeAt`.

### 2.2. Звільнення воркера і пробудження

- Воркер, отримавши `Suspended`, в одній транзакції: ставить `status = waiting`, `resume_at`, `waiting_node_id`, завершує поточний job і ставить новий job `execution` з `run_at = resume_at`. Слот воркера звільняється одразу.
- Черга вже вміє `run_at`, тож окремий планувальник не потрібен: job з'явиться у вибірці, коли настане час.
- Обробник job бачить `waiting` → переводить у `running` і викликає `ResumeAsync` зі знімка (той самий шлях, що після падіння воркера, F2-08). Вузол у `waiting` виконується повторно з `ctx.Resume` (`state` і фактичний час пробудження) і віддає items далі.
- Рестарт Api чи воркера нічого не губить: стан, знімок і job лежать у Postgres.

### 2.3. Скасування, таймаути, ліміти

- Скасування `waiting` → одразу `cancelled` (воркер не потрібен); job пробудження, коли настане, побачить фінальний стан і завершиться без виконання.
- `executionTimeoutSec` рахує лише **активний** час (`running`); час у `waiting` не рахується. Для очікування є власні ліміти вузлів (`maxWaitSec`, `timeoutAfter`).
- Ліміт одночасних виконань сценарію (F6-06) рахує лише `running`; `waiting` слота не займає.
- Найдовше очікування — 90 днів (`core.wait` v2). Більше — помилка валідації.
- Статус `waiting` і час пробудження видно в `/executions` (UI, REST, MCP `list_executions`/`get_execution`) і в SSE.

### 2.4. `core.wait` v2

- `typeVersion: 2`, режими `mode`: `duration` (`amount` + `unit`: seconds…days) і `until` (вираз дати ISO 8601). До 30 с вузол чекає в пам'яті, як v1 (немає сенсу писати стан на коротку паузу), довше — через `waiting`.
- v1 лишається без змін, тож старі сценарії працюють як раніше. Редактор пропонує v2 для нових вузлів.
- Пробудження за вебхуком чи формою — F6-01 поверх цього ж механізму.

## 3. Очікування дії людини (F5-03)

Типовий крок продажу: «створити задачу менеджеру в Кіті й чекати, поки її закриють, інакше ескалація». Кіт подій не шле, тож вузол `core.waitFor` сам опитує:

- параметри: `serverId`, `tool`, `args` (вирази), `condition` (як у `core.if`, над результатом tool'а), `interval` (від 1 хв до 24 год), `timeoutAfter` (до 90 днів);
- кожна перевірка — виклик tool'а; умова виконана → вихід `done` з останнім результатом; час вийшов → вихід `timeout`; між перевірками виконання в `waiting` (§2), лічильник і дедлайн — у `state` вузла;
- помилка tool'а — як у будь-якого вузла: зупиняє виконання або йде у вихід `error` при `continueOnFail`;
- для задач Кіта умова — `status in (Виконане, Невиконане)`; статус «Протерміноване» Кіт ставить сам кожні 5 хв, він **не** означає завершення.

Людські задачі всередині OpenBP (`core.approval`, `/tasks`) — окремий механізм F6-02; у сценаріях продажів можна поєднувати обидва.

## 4. Ключ кореляції (F5-04)

- Необов'язковий `executions.correlation_key` (текст до 200 символів) з індексом `(workflow_id, correlation_key)`.
- Задається виразом у тригері (`core.webhook`, `mcp.poll`, ручний запуск — параметр `correlationKey` вузла) або параметром REST/MCP-запуску (`correlationKey`). Для угоди — `{{ $json.Id }}` з `CrmSales`, для контрагента — його Id.
- Налаштування сценарію `settings.correlation: { skipIfActive: true }`: якщо є активне (`queued`/`running`/`waiting`) виконання цього сценарію з тим самим ключем, нове **не створюється**. Подія пишеться в системний журнал і в аудит; webhook відповідає 200 `{ skipped: true, executionId: <активне> }`; MCP/REST-запуск — 409 `EXECUTION_DUPLICATE` з id активного.
- Фільтр за ключем у `/executions` (UI, REST `?correlationKey=`, MCP `list_executions`). Так видно «які процеси йдуть по цій угоді».
- Не плутати з дедуплікацією вебхука (F6-05): та відсікає повторний HTTP-запит у вікні часу, незалежно від стану виконання.

## 5. Конектор `kit-crm` (F5-05)

MCP-сервер на Connector Kit (`connectors/kit-crm`), stdio або http, як інші конектори.

### 5.1. Автентифікація

- Токен Keycloak (realm `astarta`) через `client_credentials`: **окремий client** у Keycloak із service account (рішення власника, 2026-10-24). Env: `KIT_TOKEN_URL`, `KIT_CLIENT_ID`, `KIT_CLIENT_SECRET`.
- У таблиці `Users` Кіта має бути користувач, зв'язаний із service account цього client'а, з роллю `CRM_user`. Інакше OData відповідає 403 на запис. Client і користувача створює власник на dev-стенді.
- Токен кешується до `expires_in − 30 с`; 401 → одне оновлення токена й повтор; другий 401 → помилка tool'а «сервісний користувач не автентифікований».
- Секрети лише в env конектора (credential OpenBP типу `mcp.stdio`/`mcp.http`), ніколи у відповідях tools і журналах.

### 5.2. Обов'язкові правила запису

- Заголовок `FrontPagePath` на POST/PATCH/DELETE береться з env `KIT_FRONT_PAGE_PATH`. Поки значення немає (рішення власника: «поки ніякі, потім поставимо»), тож env порожній і заголовок не шлеться. Якщо `RolePermissionHandler` Кіта відповість 403, конектор пише зрозумілу помилку з підказкою задати `KIT_FRONT_PAGE_PATH` і перевірити роль.
- Видалення в Кіті м'яке (`IsDelete = true`). Конектор додає `IsDelete eq false` до кожного `$filter` і ніколи не повертає видалені записи.
- Відповідальний на угодах і задачах — `CrmPerson`, а не `Users`. Tools приймають і повертають `CrmPersonId`; пошук за email користувача — через `Users.CrmPersonId`.

### 5.3. Tools

Генератор з `$metadata` (F3-12) дає базові CRUD-tools; поверх них ручні, з людськими назвами й описами:

| Tool | Що робить |
|---|---|
| `find_sales { query?, stageId?, responsibleId?, updatedSince?, top? }` | пошук угод `CrmSales` |
| `get_sale { id }` · `update_sale { id, fields }` · `set_sale_stage { id, stageId }` | угода |
| `create_task { title, description?, responsibleId, managerId?, deadline, categoryId?, saleId?, personId? }` | задача `CrmTasks` (сервер Кіта сам створить сповіщення й лист) |
| `get_task { id }` · `list_tasks { saleId?, responsibleId?, status?, deadlineBefore? }` · `set_task_status { id, status }` | задачі |
| `find_contractors { query }` · `get_contractor { id }` · `find_persons { query }` · `get_person { id }` | контрагенти й особи |
| `add_sale_note { saleId, text }` | нотатка до угоди |
| `get_user_manager { crmPersonId }` | керівник менеджера з профілю користувача: `CrmPerson` → `Users` (email) → `GET /users/{email}/manager` у Microsoft Graph; повертає ім'я та email або `null` |
| `changes_since { entity: sales \| tasks \| contractors, since }` | записи з `Updated gt since` для `mcp.poll`, новий курсор = найбільший `Updated` |

### 5.4. Опитування змін

- `mcp.poll` викликає `changes_since` кожні 5 хв (підтверджено власником) і зберігає курсор `since` у стані тригера.
- Нова угода відрізняється від зміненої за `Created >= since`; сценарій фільтрує це сам (`core.if`).
- Дублікати між опитуваннями (запис змінився двічі) відсікає ключ кореляції (§4) зі `skipIfActive`.

## 6. Пілотні сценарії

### 6.1. Нова угода → задача менеджеру → контроль → ескалація (F5-06)

`examples/kit-sales-followup.json`:

1. `mcp.poll` `kit-crm.changes_since { entity: sales }` → лише нові угоди; `correlationKey = {{ $json.Id }}`, `skipIfActive`.
2. `kit-crm.create_task`: «Зв'язатися з клієнтом», відповідальний = відповідальний угоди, дедлайн +1 робочий день: понеділок–п'ятниця, суботу й неділю пропускаємо, державні свята не враховуємо (рішення власника).
3. `core.waitFor` `kit-crm.get_task` до статусу Виконане/Невиконане, `interval` 30 хв, `timeoutAfter` 2 дні.
4. `done` → `kit-crm.add_sale_note` з результатом. `timeout` → `kit-crm.get_user_manager` → лист керівнику (Graph `sendMail`) і повторна задача. Немає керівника в профілі → лист на адресу з параметра сценарію.

DoD: CLI-прогін з фейком OData Кіта й моком Graph для обох гілок; дубль угоди не запускає другий процес.

### 6.2. Щоденний звіт по протермінованих задачах (F5-07)

`examples/kit-overdue-report.json`: `core.schedule` 08:30 `Europe/Kyiv` → `kit-crm.list_tasks { status: Протерміноване }` → `core.code` групує за відповідальним → лист кожному менеджеру й зведення його керівнику (`get_user_manager`) через Graph. Порожній день — без листів.

## 7. Порядок робіт

1. F5-02 (довге очікування) і F5-04 (кореляція) — незалежні, можна паралельно.
2. F5-03 (`core.waitFor`) після F5-02; F5-05 (конектор) паралельно з ними на фейку OData.
3. F5-06, F5-07 після конектора.
4. Поверх F5-02 — F6-01 (вебхук і форма для `core.wait`), F6-04 (підсценарії).

## 8. Рішення власника (2026-10-24)

1. Сервісний доступ — окремий client у Keycloak (`client_credentials`); користувача з роллю `CRM_user` створює власник.
2. `FrontPagePath` — поки не задаємо, значення поставимо пізніше.
3. Робочі дні — понеділок–п'ятниця, без довідника свят.
4. Ескалація — листом; керівник береться з профілю користувача (Microsoft Graph `manager`).
5. Інтервал опитування угод — 5 хв.
