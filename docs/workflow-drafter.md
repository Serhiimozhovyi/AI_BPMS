## Чому нинішній помічник не годиться для локальної моделі

Помічник F3-60 (`AssistantService`) розрахований на сильну хмарну модель:

- `describe_nodes` віддає всі типи вузлів з повними JSON Schema параметрів — десятки тисяч символів; Ollama за
  замовчуванням тримає 4–8 тис. токенів контексту і **мовчки обрізає** початок розмови (системну інструкцію);
- модель має сама написати **повне** визначення сценарію (`update_workflow`) — 7–14B-моделі ламають JSON, вигадують
  `type`, гублять з'єднання;
- вільний цикл tool-calls до 20 кроків і 120 с: локальна модель на Mac відповідає повільніше, а виклики інструментів
  у малих моделей нестабільні.

## Підхід: план → компіляція → параметри → перевірка

Модель робить лише те, що вміє добре — розуміє текст і вибирає з короткого списку. Решту робить код.

1. **План (один запит, структурований вихід).** Модель отримує опис користувача, компактний каталог (тип вузла,
   назва, один рядок опису; дії конекторів — `serverId`/`toolName`/назва) і 2–3 приклади «опис → план». Відповідь
   обмежена JSON Schema (`format` в Ollama, `response_format: json_schema` в OpenAI-сумісних):

   ```json
   {
     "title": "Заявка на відпустку",
     "lanes": ["Працівник", "Керівник", "Кадри"],
     "steps": [
       { "id": "s1", "kind": "trigger", "title": "Працівник подав заявку", "lane": "Працівник", "use": "core.form" },
       { "id": "s2", "kind": "approval", "title": "Керівник погоджує", "lane": "Керівник", "use": "core.approval" },
       { "id": "s3", "kind": "action", "title": "Записати в таблицю", "lane": "Кадри", "use": "mcp:<serverId>/<toolName>",
         "hint": "дата початку, кількість днів" }
     ],
     "links": [
       { "from": "s1", "to": "s2" },
       { "from": "s2", "to": "s3", "branch": "approved" }
     ]
   }
   ```

   `kind` — закритий список (`trigger`, `action`, `condition`, `approval`, `wait`, `transform`, `notify`, `end`);
   `use` — лише значення з каталогу (`enum` у схемі), невідомий інструмент → `"none"`.
2. **Компіляція (код, без моделі).** План → `WorkflowDefinition`: id вузлів, `type`/`typeVersion`, порти виходів за
   `branch` (з дескриптора вузла), розкладка зліва направо по рангу в графі, бізнес-атрибути (`business.lanes`,
   `node.business.lane`, F3-67) — щоб одразу працював «Бізнес»-вигляд.
3. **Параметри (по запиту на вузол).** Для кожного вузла з обов'язковими параметрами — окремий короткий запит:
   опис процесу, крок плану, назви попередніх вузлів і **схема лише цього вузла** як структурований вихід. Секретів і
   `credentialId` модель не заповнює ніколи.
4. **Перевірка і повтор.** Валідатор сценарію (`IWorkflowService.ValidateAsync`). Помилки плану (невідомий `use`,
   крок без зв'язку, кілька тригерів) повертаються моделі текстом — до 2 повторів плану; помилки параметрів — до 2
   повторів для конкретного вузла. Що не вдалося — лишається на вузлі як звичайна помилка валідації з підказкою.
5. **Результат.** Подія `definition` у редактор (як у помічника: звичайна правка, `undo` скасовує) і список
   «Що доналаштувати»: вузли без підключення, без облікових даних, кроки з `use: "none"`.

Підхід однаковий для всіх провайдерів: хмарна модель теж виграє (дешевше, швидше, передбачуваніше).

## Ollama як провайдер

Окремий тип облікових даних `ollama` (`baseUrl`, `contextLength`, `keepAlive`), рідний API `POST /api/chat`:
`options.num_ctx` задається з облікових даних (OpenAI-сумісний `/v1` його не приймає), `format` — JSON Schema,
`think: false` для моделей з міркуванням, `tools` — для помічника F3-60. Перевірка з'єднання — `GET /api/tags`:
список моделей і чи підтримують вони `tools` (`POST /api/show` → `capabilities`).

Docker на Mac: Api в контейнері ходить на `http://host.docker.internal:11434`.

## Які моделі реалістичні

| Розмір | Приклади | Очікування |
|---|---|---|
| 7–8B | qwen3:8b, llama3.1:8b | лінійні процеси на 3–5 кроків; українську розуміє посередньо |
| 12–20B | qwen3:14b, gemma3:12b, gpt-oss:20b | процеси на 3–10 кроків з умовами й погодженнями — основна ціль |
| 27–32B | gemma3:27b, qwen3:30b-a3b, qwen3:32b | найкраща якість локально; потрібно 32 ГБ+ пам'яті |

Mac власника (2026-10-28): M3 Pro, 18 ГБ, Ollama 0.40; встановлені `qwen3:8b`, `qwen3:14b`, `qwen3.5:4b`,
`gemma4:e2b-it-qat`, `gemma4:26b`. Ціль — `qwen3:14b` (≈9,3 ГБ ваги + контекст 16k ≈ 11–12 ГБ), запасна — `qwen3:8b`;
`gemma4:26b` (18 ГБ) у пам'ять не вміщується. Міркування в qwen3/gemma4 увімкнене за замовчуванням — вимикаємо (`think: false`).

Цифри підтверджує набір еталонних описів (F3-105), а не відчуття.

## Замір моделей (F3-105)

`tests/drafter-cases/*.json` — 15 описів українською, від «щоранку надсилати звіт у Telegram» до погодження з ескалацією
й кількома доріжками (формат `expect` — `tests/drafter-cases/README.md`). Команда проганяє їх проти запущеного OpenBP
через `POST /workflows/{id}/draft` (модель — та, що вибрана в «Налаштування → Помічник»; `--workflow` — будь-який
сценарій, його вміст не змінюється):

```bash
export OPENBP_URL=http://localhost:8088 OPENBP_API_KEY=…   # ключ — «Налаштування → API-ключі»
dotnet run --project src/OpenBP.Cli -- draft-eval --workflow <id> --model qwen3:8b --out qwen3-8b.md
```

Таблиця: валідність сценарію (`/workflows/validate`), збіг структури з `expect`, повтори (кроки `retry`), час. У CI
механізм перевіряється на фейковому провайдері (`DrafterTests`, `DraftEvalTests`); живий прогін — лише вручну на Mac і
лише за згодою власника (16 ГБ пам'яті вже ледве вистачало): спершу `qwen3:8b` (контекст 8k, `keepAlive` ≈ 1 хв), `qwen3:14b` —
якщо 8b не вистачає; `gemma4:26b` не запускати.

| `qwen3:14b` | не заміряно | не заміряно | не заміряно | не заміряно | — |
