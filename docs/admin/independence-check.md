# Протокол перевірки незалежності продукту

Критерій фази 7 ([roadmap](../roadmap.md), [ADR-004](../adr/ADR-004-stages.md)): другий застосунок підключається до
AI_BPMS через той самий контракт етапів, що й «Кіт 2», **без змін у `src/`**, а в коді продукту немає жодної клієнтської
системи. Перевірка має дві частини: автоматичний архітектурний тест і прогін контракту другим застосунком.

## 1. Архітектурний тест

`tests/OpenBP.Architecture.Tests/ProductIndependenceTests.cs` (CI: `dotnet test`) сканує `src/` і `apps/web/src`:

- сутності й адреси клієнтів: `CrmSale`, `CrmTask`, `CrmPerson`, `lams`, `lams-kit`, `odata/`, `KitCrm`, `kit_crm`;
- ідентифікатори всіх конекторів з `connectors/*/connector.json` (зараз `kit-crm`, `psy-support`), крім універсальних
  `telegram`, `onec`, `msgraph` (канали зв'язку й облікова система з каталогу продукту: канали сповіщень, перенесення з
  n8n, підказки в схемах). Новий конектор за замовчуванням клієнтський, доки його свідомо не внесено до
  `GenericConnectors`.

Винятки — словник `Exceptions` у тесті, кожен із поясненням; тест падає, якщо виняток більше не потрібен. Зараз це два
файли з довільним підписом кроку `kit-crm` у вхідних даних Vitest. Тест перевірено на навмисному порушенні: рядок
`// CrmSale` у `src/OpenBP.Shared` робить `Product_code_names_no_client_system` червоним з указанням файла й рядка.

## 2. Прогін контракту другим застосунком

Другий застосунок — психологічна підтримка (`connectors/psy-support`), сценарій
[`examples/psy-support-case-stages.json`](../../examples/psy-support-case-stages.json): «Прийом» → «Оцінка психолога»
(`core.approval`) → «Закриття», з правилами `r_risk` (ризик ≤ 3, `warn`) і `r_conclusion` (є висновок, `warn`).
Застосунок користується лише публічним контрактом: REST `/api/v1/executions/{id}/stages` та `…/actions/{actionId}` і
MCP `get_execution_stages`, `act_on_stage`, resource `openbp://executions/{id}/stages` з API-ключами ролей `editor`
(психолог) і `viewer` (стажер).

- **Дата:** 2026-10-26.
- **Версія:** `main` @ `7e2520c` (після F7-05); зміни в `src/` для прогону — жодних (`git diff -- src` порожній).
- **Середовище:** хмарний Linux-контейнер, PostgreSQL 16 у Docker, Api і Worker через `dotnet run`, міграції
  `dotnet ef database update`. Користувачів психолога й стажера заведено SQL-командою з [посібника §5](README.md).
- **Хто:** Claude, задача F7-08.

| # | Що робили | Результат |
|---|---|---|
| 1 | `POST /workflows` зі сценарієм-прикладом; `POST /workflows/{id}/executions` ключем психолога | ✓ 201 і 202; виконання зупинилось у `waiting` на задачі погодження |
| 2 | `GET …/stages` ключем психолога | ✓ «Прийом» `done` з відкритим порушенням `r_risk` і дією `override:r_risk`; «Оцінка психолога» `active` з дією `task:{id}`; «Закриття» `pending` |

## Що виявила перевірка

- Повідомлення 422 при правилі, чий `message` закінчується крапкою, дає «..» перед «Вкажіть причину»: стилістична
  дрібниця, що не заважає підключенню; виправлення — в `StageService` (`src/`) окремою правкою.
- Створити користувачів з ролями `editor`/`viewer` можна лише SQL-командою (немає REST) — вже відомий розрив фази 4.
- Адмінка `connectors/psy-support/web` поки не викликає контракт етапів: прогін виконано клієнтом із публічного REST/MCP
  з ключами ролей. Вбудувати `<openbp-canvas view="business" execution-id>` в адмінку можна без змін у `src/`; це
  окрема задача застосунку.
